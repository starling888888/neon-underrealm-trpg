# milestone-02-phase-02-gm-section

## 目的

ネオン・アンダーレルムTRPG公式ルールサイトへ、初期作成PCを対象とするGMセクションを追加する。

GMが参照・運用できるルールとエネミー情報を公開するため、以下を公開する。

- GMセクション開始の案内
- エネミーデータの見方
- ボスデータの作り方
- 三下・徒党データの作り方
- キャンペーンフック
- サンプルシナリオ一覧
- 完成済みのサンプルシナリオ1本

本issueは、最初のサンプルシナリオ1本を含むGMセクションの初回公開までを対象とする。

2本目以降のサンプルシナリオは本issueへ含めず、1シナリオにつき1つの後続issueとして逐次追加・公開する。

## 背景

プレイヤー向けセクション、Webキャラクターシート、サポートページは公開済みであり、現在はGM向けセクションの新規作成フェーズである。

サンプルシナリオには、共通ボス、機龍、悪魔、三下、徒党、外道スキルなど、プレイヤー向け公開ページだけでは読み方が分からないGM専用情報が含まれる。

このため、サンプルシナリオだけを先行公開しない。

先に以下を完成させる。

1. エネミーデータの分類と読み方
2. ボスデータの作り方
3. 三下・徒党データの作り方
4. シナリオ作成の出発点となるキャンペーンフック

これらを参照できる状態にした後、サンプルシナリオ1本を完成させ、GMセクション全体を初回公開する。詳細なGMガイド本文は、この初回公開の対象外とし、`docs/TODO.md`で後続taskとして追跡する。

## エネミーデータの分類

GMセクションでは、エネミーデータを以下の4形式に分類する。

### 共通ボスデータ

以下は同じ基本データ構造と表示Componentを使用する。

- 外道
- PC相当＋α
- ホムンクルス

外道は、PCに近いスキル構成で戦い、通常スキルに加えて外道スキルを取得できる。

ただし、外道データをPCデータと完全に一致させることは前提としない。

PC相当＋αは、PCに近い構成へボス用の能力、数値、特殊能力などを追加したデータを指す。

ホムンクルスも、現時点では共通ボスデータ形式で表現する。

### 機龍データ

機龍は、以下の固有構造を持つため専用データ形式とする。

- 機龍共通ルール
- 特殊障壁X
- 機械の体
- イニシアチブと行動回数の組を複数持つ「複数回行動」
- 複数の専用攻撃
- 攻撃ごとの範囲、追加効果、使用制限
- 特殊攻撃への通常リアクションを行わない処理
- 機龍固有の特殊能力

機龍を共通ボスComponentへ無理に統合しない。

### 悪魔ボスデータ

悪魔ボスは、悪魔本体と契約者の2体を一組として扱う複合データ形式とする。

以下の悪魔共通ルールを、悪魔本体と契約者の上位に表示する。

- 契約とともに
- 半実体
- 悪夢の強化X
- ただの人間

悪魔本体と契約者それぞれの数値データは、共通ボスデータ形式を使用する。

悪魔専用Componentは、契約ルールと2つの共通ボスデータを束ねる責務を持つ。

### 三下・徒党データ

三下は、固定達成値と固定ダメージを中心とする独立した簡易データ形式とする。

三下を共通ボスComponentへ統合しない。

徒党は、三下を集団として扱うルールとして三下データと同じページで説明する。

## 実装方針

### 画面単位で完成させる

ページ、データ変換、表示Component、テスト、デザイン確認を、横断的な基盤Gateへ分離しすぎない。

各Gateでは、対象ページに必要な以下をまとめて完成させる。

- 本文
- 必要な構造化データ
- データ変換
- 検証schema
- 表示Component
- サイトメニュー
- 内部リンク
- 自動test
- Visual Review
- desktop、tablet、mobileの実画面確認

共通Componentは、最初に実利用するページのGateで作成する。

後続ページで実際に再利用または拡張する必要が生じた場合だけ、既存Componentへ変更を加える。

将来利用を想定した空Component、巨大な共通型、汎用エネミー基盤を先行作成しない。

### ページの公開順

各Gateの成果は親branchへ順次統合するが、`main`へはmergeしない。

サンプルシナリオ1本を含む全Gateが完了した時点で、本issue全体を`main`へmergeし、GMセクションを初回公開する。

GMガイド、エネミーページ、キャンペーンフックだけを個別に先行公開しない。

サンプルシナリオだけも先行公開しない。

## Gate関係

- 親issue：本issue
- Gate plan：`docs/issue/milestone-02-phase-02-gm-section/plan.md`
- 親branch：`milestone-02-phase-02-gm-section`
- 各Gateは専用の子issueと子branchで実装する。
- 子branchは、着手時点の最新親branchから作成する。
- 子branchのPRは親branchをbaseとする。
- 子branchを直接`main`へmergeしない。
- 各Gateの詳細な実装契約は子issueを正本とする。
- Gateの一覧、依存、順序、公開条件はGate planを正本とする。
- 全Gate完了後に、親branchから`main`への最終PRを作成する。

## Gate着手前提

- 着手対象はG1のみとする。G1の子issueを作成・承認するまで、source codeを変更しない。
- G1では、既存layout内に短い案内本文だけを置く。ユーザー指示により、新規design notes、design画像、VRT baselineは作成しない。
- G2で使用する機龍、悪魔ボス、外道スキルSpreadsheetなどの入力は、G1完了後にユーザーが提供する。提供前にG2の子issue、子branch、変換script、schema、表示Componentを作成しない。
- G2以降のUI Gateは、各Gateの子issue作成時に対象routeのdesign target、承認済みdesign画像、VRT参照情報を定義する。design入力が不足する場合は、`design-image-generation`を先行する。

外道、PC相当＋α、ホムンクルスで共通使用する表示Componentを作る。

仮称は`BossEnemySheet`とする。

少なくとも以下を表示できるようにする。

- エネミー種別
- 最大体力
- 最大精神力
- 行動値
- 移動力
- 行動回数
- 防御力
- ダメージ軽減

- 通常スキル
- 外道スキル
- 特殊能力
- 行動指針
- 備考

外道スキルは任意項目とする。

外道の場合だけ、変換済み外道スキルデータを参照して表示できるようにする。

### サンプルシナリオの追加構造

最初のシナリオGateで、後続issueから1本ずつシナリオを追加できる構造を確定する。

後続シナリオの追加作業は、原則として以下に限定できるようにする。

- シナリオMDXの追加
- 必要なシナリオ固有アセットの追加
- 一覧表示用metadataの追加
- サイトメニューへの追加
- 必要なエネミーデータの追加
- 対応testの追加
- Visual Review
- リリースノート

一覧とサイトメニューの整合を保つために単一の静的metadata定義が必要な場合は、最初のシナリオGateで最小限の定義を追加してよい。

実際に使用しないfieldを将来用として追加しない。

シナリオCMS、管理画面、DB、動的登録機構は作らない。

## branch・公開方針

### 親branch

親branch名は以下とする。

`milestone-02-phase-02-gm-section`

親branchは`main`から作成する。

### 子branch

各Gateの子branchは、着手時点の最新親branchから作成する。

各子branchのPRは親branchをbaseとする。

各Gateの完了・レビュー後に、子branchを親branchへmergeする。

子branchを直接`main`へmergeしない。

### 公開

G1からG5までの途中成果を公開しない。

G6のサンプルシナリオ1本が完成し、親issueの完了条件をすべて満たした後、親branchから`main`へのPRを作成する。

`main`へのmergeによって、以下を同時に初回公開する。

- GMガイド
- エネミーデータの見方
- ボスデータの作り方
- 三下・徒党データの作り方
- キャンペーンフック
- サンプルシナリオ一覧
- サンプルシナリオ1本

未完成ページ、空ページ、将来用メニュー項目を公開成果物へ含めない。

## 後続サンプルシナリオ
